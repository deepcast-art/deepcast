## THE CLAIM-LINK FLOW (CURRENT — how films travel now, July 2026)

Invites are LINKS, not emails. A sharer enters only the invitee's first name and gets a link; the invitee claims it with their email alone (email-only form since 2026-08-06) and watches immediately (the claim creates their account — see the claim route). Recon + full design history: `PLAN.md` and `deepcast-mvp-rework.md` (its decisions log is binding).

### Server routes (`server/index.js`)

- `POST /api/invites/create-link` — two sharer-identity paths (both set `parent_invite_id`, unified lineage model): a **verified session** (Bearer → `getUser()`, reusing the exact parent-resolution fallbacks of the legacy send route), or a **claimed invite reference** (`server/claimIdentity.js` — the claim IS the identity; no session needed). Since Pieces E/F the wallet fork keys on ACCOUNT existence, never on the session: a `claimed_by`-backed sharer spends their per-film `film_tickets` wallet (server-resolved, `sender_id` stamped on the child — unified lineage), and only account-less rows fall back to the invite wallet's CAS. Slug generation in `server/inviteSlug.js` (owner ruling 2026-07-21 — neutral slugs): the fixed word `ticket` + hyphen + a 5-char suffix from the unambiguous alphabet (no 0/o/1/l/i), 3 retries then widen to 6; **the typed first name never feeds the URL** (names come only from `invites.recipient_name`); reserved-route blocklist kept, plus a startup guard that refuses if `ticket` ever becomes a route. Old name-based slugs (pre-2026-07-21) are never rewritten and resolve forever.
- `GET /api/invites/link/:slug` — public landing/watch payload (names, lineage, hook, posterUrl, muxPlaybackId, tickets, `ticketNo` — the permanent ticket number, present for unclaimed and claimed links alike, null when the row has none — and, since 2026-09-09 (branch `rail-onward`), `onward: [{ firstName, claimed }]` — the people THIS invite's holder shared with directly: its non-void child rows, oldest first, first names through `safeFirstName`, `claimed` by the shared claimed-stage rule; nothing else about them; `buildOnward` in `server/watchPayload.js`, unit-tested; the film-scoped route serves `onward: []`; older frontends ignore the field). Never exposes the legacy `token`. Never transitions status. **Owner revisit of a claimed link routes by progress (2026-07-21):** the stash-recognized owner is bounced to `/dashboard` once the film is completed (the shared `isInviteWatched` rule in `src/lib/filmStats.js` — 70%-watched, the same bar as the ticket statuses), else to their watch page; strangers still get the dead-link page.

- `GET /api/films/:filmId/watch` (2026-09-03) — the filmmaker's own watch page: the SAME payload shape as the link route (film-level fields from the shared `buildFilmWatchFields`; the invite-level fields honestly null: no names, `lineageNames: []`, `lineageForks: []`, `inviteId: null`, `ticketNo` = `films.creator_ticket_no`, `ticketsRemaining: null`) plus `filmId`, `creatorName`, and `ticketsUnlimited` (`isRoleUnlimitedSharer` on the caller's profile). Verified-session pattern: Bearer → `getUser()`; ownership = `films.creator_id` equals the token's user (`filmWatchDecision`, `server/watchPayload.js`) — 401 without a session, 404 for an unknown film, 403 for anyone else including team members and other creators.
- `POST /api/invites/claim` — the email IS the claim, accompanied by silent context (2026-07-31). **Full name (SERVER PATH ONLY since 2026-08-06):** the landing page no longer sends a name (email-only form — founder decision 2026-08-06), so every claim-link claim takes the legacy naming fallback (recipient_name → email local part). The server-side `fullName` handling stays intact for compatibility (old tabs, future surfaces): when present it is re-validated (`fullNameInputError`), its FIRST word becomes the account's first name and the remainder becomes `users.last_name` via `findOrCreatePasswordlessAccount`. Last names are DATA, never display — every surface stays first-name-only. **Silent context capture (owner-approved in-session 2026-07-31):** the browser's timezone, language, and coarse device class ride the claim and stamp `invites.claim_timezone` / `claim_locale` / `claim_device` (migration `20260731_claim_context.sql`, applied via the approved path and INDEPENDENTLY verified through `information_schema`) — sanitized by `sanitizeClaimContext` (`src/lib/claimContext.js`, device restricted to phone/tablet/desktop), non-fatal at every layer: blocked browser APIs send nothing, junk is dropped, missing columns fall back to claiming without capture. Atomic race-guarded UPDATE (`eq status 'created'` + `is claimed_email null`); stamps `claimed_email`, `claimed_at`, `status='claimed'`, the frozen `claim_ordinal` (+ the context fields); creates (or attaches to) a passwordless account, stamps `claimed_by`, initializes the film's `film_tickets` wallet at 5. **The claim SIGNS THE NEW USER IN (Fix A, 2026-07-21):** for a freshly CREATED account only, the server mints an in-band single-use sign-in (`generateLink` → client `verifyOtp`, no email) — an ATTACHED pre-existing account NEVER gets a session from a typed email (they use the normal sign-in flow). **The client's `verifyOtp` exchange is deadline-bound at 8s since 2026-07-31** (`withTimeout` in `src/lib/withTimeout.js`, unit-tested): a hung exchange can no longer strand the claimer on "One moment…" — past the deadline the claim proceeds exactly as a failed exchange always did (non-fatal by construction). **Duplicate-claim guard (Fix B + amendment):** if the email already holds this film, the fresh link is VOIDED (`status='void'`, race-safe — can never destroy a real claim; its ticket number dies with it, permanent gap), the sender's ticket auto-refunds (`server/voidRules.js` — skipped for role/wallet-unlimited senders; `team_creator_id` only ever read), and the claimer sees "You already hold this film." before routing to their dashboard. The sharer's own session never claims; the film never travels back to its maker (`server/shareRules.js`). Routes to the watch page through the once-per-claim PROLOGUE (founder spec 2026-07-21, `ClaimPrologue` in `ClaimLanding.jsx`): a full-screen interstitial on the brand ink background (softened 2.5x + timing polish, owner revisions 2026-07-21: 2.5s line fades at 0/3/6s, ~3s hold, 3s dissolve beginning ~11.5s in), three staggered italic serif lines (each staying once shown, ONE uniform style, no bolding) — "{Receiver}, {Sharer} saw this and thought of you." / "No algorithm sent you this. A person did." / "After watching, you'll do the same — choose the few people who need it next." (wording revised by founder approval 2026-07-24) — tap/Enter/Space to advance (first tap reveals all, next skips), reduced-motion renders all three lines statically and HOLDS until a tap/Enter/Space — no timed auto-advance (2026-07-31; the old ~4s hold was field-verified too short to read) — and it warms the watch chunk + Mux preconnects + poster while holding. NO storage: it exists only in the claim-success state, so duplicates, sharer-view, dead links, voids, and revisits structurally never see it. Its dissolve hands off to the watch page's 1s arrival fade via the in-memory `fromPrologue` router marker (cosmetic only — the once-per-claim guarantee never depends on it).

- **`POST /api/invites/return { token }` (2026-09-16):** hashes the token, looks the invite up by `return_token_hash`; the decision is `returnLinkDecision` in `server/returnLinkRules.js` (unit-tested — `spent` is answered before `expired`, so a used-then-aged link still prefills the email); answers 200 with a `status` — `ok` (spends it by a conditional update where `return_token_used_at` is null — a replay or a second tab sees `spent`; mints the in-band single-use sign-in for the claimant's account ONLY when the claim holds an account (`mayMintSession` — an accountless claim arrives on the stash alone, so `generateLink` can never sign a fresh auth user up) and returns `slug`, `inviteId`, `filmId`, `email`, `sessionTokenHash`), `spent` (+ `email`), `expired` (past `RETURN_TOKEN_DAYS`, 180), `unknown` (no such hash, a void or unclaimed row, or the columns not yet migrated); a malformed token is 400. The plaintext is never logged and never in a query string (the bare `GET /r/{token}` does land in Vercel's access log — a spent token within milliseconds). **Security-doctrine note:** this route is pinned to possession of the emailed token, not to a session — that is its purpose; the token grants one sign-in to the account that claimed the ticket, the same account the ticket email reached, and nothing else. **The 180-day life (re-minted by each reminder; the founder's figure, follow-up 3 — was 30) is the design's security parameter — a Supabase magic link lives about an hour.** The landing consumes the `returnArrival` router-state marker IN PLACE (`history.replaceState` on the entry, never a router navigation), so a reload mid-prologue or Back from the film is an ordinary owner visit — e2e-asserted with a real reload on every engine (the Back step on chromium and firefox; WebKit's back-forward cache under Playwright re-fetches past the route mock — a harness artifact, noted in the spec). **Deploy order:** the migration must be applied BEFORE this code is live — until the columns exist the ticket email's button links to the bare slug, which is the dead-link page on a fresh device (the log says `[return-token] not stored`).

- `POST /api/invites/replenish-check` — the +3-per-3-watched viewer replenish, per-film, server-recomputed (Piece F; the old client-side write of another user's row was RLS-dead). Called from the legacy screening where `checkReplenish` ran.
- `GET /return` (client route, `src/pages/ReturnGate.jsx`) — where magic sign-in links land: routes to the most recently claimed UNWATCHED film's watch page; all watched or no claims → `/dashboard`. Never dead-ends for any authenticated user; `claimed_by` primary, `claimed_email` fallback.

### Tickets (PER-FILM economy — Piece F, 2026-07-18)

One wallet per (person, film): **`film_tickets(user_id, film_id, balance, unlimited)`**, migration `20260717_film_tickets.sql` (applied). Rows are LAZY — a missing row reads as the virtual full grant of 5 and materializes on first write; claiming a film initializes that film's wallet at 5. Spent at link GENERATION, no refunds (a failed generation is refunded — that's not a spend); race-safe spend/grant/refund live in `server/filmWallet.js`; canonical display is `filmTicketsRemaining(profile, wallet)` in `src/lib/shares.js`. EVERY spend path goes through the film wallet: legacy `/api/invites/send`, both create-link branches (session, and stash-based via `claimed_by` — `server/claimantWallet.js`), the admin grant, and the server-side replenish. **`users.invite_allocation` and `users.unlimited_shares` are DORMANT** — still written at account creation, never read on ticket paths. The legacy invite wallet (`invites.tickets_remaining`, `src/lib/ticketRules.js`) survives ONLY as the degradation path for claimed rows with no account (claimed_by NULL). Zero state: "You've shared all your tickets for this film." (verb per the 2026-07-25 vocabulary ruling) — no upsell, and now truthfully per-film.

### Ticket numbers — LIVE, permanent, immutable (2026-07-22)

Per-film sequential numbers, minted atomically at GENERATION by `next_ticket_no()` (`films.ticket_seq`; service-role only; non-fatal — numbering can never block a share). **The filmmaker always holds №1** (`films.creator_ticket_no`, migration `20260722_creator_ticket_no.sql`, applied; new films are born with the counter at 1 by column default), shown on the creator dashboard's film cards and under FILMMAKER at the constellation's center. **Invitees start at №2. Numbers are IMMUTABLE: deletions leave permanent gaps; NOTHING ever renumbers an invite.** Ghosts and voided links are never numbered (`needsTicketNumber`). Assigned as of the 2026-07-22 backfill: The New Narrative — Trace №2, Austin №3, Tina №4, Georgie №5. A Sacred Pause — №2 was Jon's original test invite, removed by the owner via admin Remove on 2026-07-21 ahead of the live demo claim; №2 is now a permanent gap and the next generated ticket mints №3. **`server/backfill-ticket-numbers.js` and `server/delete-orphan-rows.js` are COMPLETED one-time operations — do not re-run** (both are dry-run-by-default and state-guarded if ever touched).

### Ordinal freeze

`invites.claim_ordinal` is stamped ONCE at claim ("Nth person invited to this film" at that moment) and never recomputed; the dashboard displays it via `formatOrdinal` (`src/lib/ordinal.js`). Pre-claim displays may compute live.

### Lineage thread (`src/lib/lineageThread.js` — unit-tested grammar)

Built from `parent_invite_id` ancestry (walked server-side in the link route, one film-scoped query). Label above it: "How this reached you". Total nodes ≤ 4 → every first name (`[Ien] —— [Dan] —— [you]`); ≥ 5 → collapse the middle to "⋯ N hands ⋯" keeping three anchors (origin, direct sharer, you), N = total − 3. First-naming happens in the lib; the slug is routing only and never a display source.

### One tier — everyone is a signed-in user (Fix A, 2026-07-21; the claimant tier is GONE)

There is no account-less claimant and no stash-based dashboard admission anymore. Claiming creates the account AND signs the browser in (see the claim route above), so `/dashboard` has ONE path for everyone: `ProtectedRoute` + `ViewerShareGate` (which admits never-shared claimants by `claimed_by`). The old pseudo-profile, `DashboardGate` stash admission, and every claimant-only branch were deleted — do not reintroduce them. Verified before removal: ZERO account-less claimants existed in production. The claim stash (`src/lib/claimStash.js`) survives ONLY as the watch page's same-visit ownership recognition and resume-key scoping — it never grants dashboard access; a stash-only browser reaches the sign-in page (never a blank one — the no-blank-page rule holds via ProtectedRoute's spinner/redirects).

**Return visits:** magic sign-in links work for everyone (Login submits with `redirectPath: '/return'`; `/return` routes to the most recent unwatched claim's watch page, else `/dashboard`). Supabase Auth → Redirect URLs must include `{site}/return`.

### Who exists — ONE definition for every surface (`src/lib/inviteExistence.js`)

The single source of truth for which invite rows count: voided links count NOWHERE (constellation, journey line, tickets given, funnel, admin table, backfill — but stay visible in the sender's ticket list as ledger history), and demo ghosts are excluded everywhere except admin surfaces (the module's `includeGhosts` parameter, owner decision). **New surfaces must read this module — never write a private filter.** **Per-film ghost visibility (`films.show_ghosts`, migration `20260722_show_ghosts.sql`, applied; owner ruling 2026-07-22):** default false = exactly the behavior above; when the owner flips it true for a STAGING/DEMO film, the viewer surfaces (constellation, journey counts, ticket rows/Shared-to-N, tickets given) include that film's ghosts as ordinary, indistinguishable nodes — threaded as `includeGhosts` from the film row through `Dashboard.jsx` → `ViewerDashboardV5` → the libs. Ghosts are NEVER ticket-numbered regardless of the flag (`needsTicketNumber` ignores it), admin surfaces are unaffected, and flag-off films are asserted byte-identical to pre-flag behavior in the lib tests. `needsTicketNumber` is the numbering rule (unnumbered + exists); `countTicketsGiven` is the given-count; `safeFirstName` (`displayName.js`) is the display-name rule (an email or any fragment of one is NEVER rendered as a name — placeholder "Someone").

### Whose name — the canonical-name rule (ratified 2026-07-23)

**A person's own account name is their one true name everywhere; the name their inviter typed is only a placeholder until they claim.** On every surface — landing headline, lineage chain, constellation and graph labels, ticket rows — a CLAIMED invite's person renders as their account's current name, and renames propagate everywhere (including into OTHER people's views of them — ratified, no softening). UNCLAIMED invites keep showing the typed `recipient_name` (the only name that exists yet).

- **Mechanism is materialize-on-write, NEVER resolve-at-render.** RLS makes render-time resolution impossible (users rows are readable own-row/team-only — verified in `pg_policies`), and a second resolution path would let surfaces disagree. `invites.recipient_name`/`sender_name` are the ONE render source every surface reads (unchanged readers: `displayName.js`, `ticketRows.js`, `constellationLayout.js`, `graphLayout.js`, `networkPeople.js`, the server lineage builder); `users.name` is the authority that writes them, at exactly three moments:
  1. **Creation** stamps the sender's account name (`/api/invites/create-link`, `/api/invites/send`).
  2. **Claim** re-stamps `recipient_name` from the claiming account's name (`server/claimNameRule.js`, unit-tested): an ATTACHED account's current name always stamps, and — since the full-name-at-claim work, 2026-07-31 — a CREATED account stamps too **when the claimant themselves typed the name it was born with** (`claimantNamed`). *(Dormant on the claim-link flow since 2026-08-06: the email-only landing form sends no typed name, so created accounts take the legacy no-name path — which never stamps, its name may be email-derived. The rule stays live for attached accounts and any future name-carrying surface.)* Blank or @-containing account names never stamp on any path — an email fragment is never written as a name.
  3. **Rename** (`handleSaveName`, `Dashboard.jsx`) propagates to sent rows by `sender_id` and to received rows by `claimed_by` + `claimed_email` (+ legacy `recipient_email`). Claim-flow invites store `recipient_email` NULL, so the old email-only match reached nothing — that was the 2026-07-23 fix.
- **Every propagation write is row-filtered — never a bare table-wide update** (e2e-guarded in `viewer-dashboard-v5.spec.js`): ghosts and strangers are structurally unreachable. Ghosts are never claimed (`claimed_by`/`claimed_email` NULL on all 149 seeded rows, verified), so they keep their typed names automatically — no guard code exists or is needed.
- **Pre-claim surfaces greet the typed name by design** (landing letter, prologue — "the letter was addressed to that name"); the account name takes over at the claim (owner decision 2026-07-23).
